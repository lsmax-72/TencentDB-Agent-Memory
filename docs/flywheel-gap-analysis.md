## 0. 为什么这篇比之前那篇重要

之前读的是 Hermes Agent 解析（阿里妹）。那篇讲的是**一个具体系统怎么实现的**，可以对照，但不构成框架。

**这一篇不一样。它是框架，而且它的三条核心立场是对着我们写的：**

| 博客的原则 | 我们的处境 |
|---|---|
| ① **自进化的瓶颈不是任何一个技术点，而是环节之间的衔接。** "大多数团队不是某个环节做得不好，而是环节之间的数据通路是断的" | **命中 #2**。我们评测跑了、数字有了，但它进不了选择链路 |
| ② **评测的可信度 > 系统的复杂度。** "错误的正反馈会让 Agent 加速开往悬崖" | **命中 #9**。我们建了一套复杂的平行栈，而判分器从没验过 |
| ③ **记忆系统的核心不是存储能力，而是治理能力。** "存 100 条低质记忆不如治理好 10 条高质量记忆" | **命中 #6**。我们的资产是一次性冻结的 JSON，没有版本、遗忘、淘汰 |

它还有一句话几乎是我们项目的墓志铭：

> **拆开来做，每一块都能说"我做了"，但合在一起却不产生复利——因为环节之间的数据通路是断的。**

## 1. 四条数据通路：我们断了哪几条

博客说飞轮能转的前提是"**每个环节的输出，恰好是下一个环节的输入**"，并列出四条关键通路：

| 通路 | 博客的说法 | 我们的状态 |
|---|---|---|
| **一：评测 → 记忆** | 评测产出"好经验"信号，触发策展式写入。断了 → "做对了但不会记住，下次还是从零开始" | ⚠️ **半断**。我们有 `evidence.json`，但 `refine.py` 丢掉 `arguments`/`result`/`failure_class`，记住的是残缺的（**#4**） |
| **二：评测 → 落地** | 评测产出"问题/差距"信号，驱动修复方案生成。断了 → "知道自己有问题但不会去改" | ✅ **通**。诊断链路有 |
| **三：落地 → 控制 → 生效** | 修复方案经门控+人工确认后上线。断了 → "**修复方案生成了但永远停在'候选'状态，不会真正影响 Agent 行为**" | ❌ **完全断**。这就是 `promotion_allowed: false`（**#2c**） |
| **四：生效 → 下一轮评测（回流）** | 这是飞轮持续转动的关键。断了 → "进化是一次性的" | ❌ **断**。我们的资产是一次性冻结的 `frozen/refinement-r2/`（**#6**） |

> **博客原文那条对通路三的描述，一字不改就是我们的状态：**
> "修复方案生成了但永远停在'候选'状态，不会真正影响 Agent 行为。"
>
> 我们甚至连"候选"都没有——我们的证据停在了一个 `research_only: true` 的抽屉里。

**这解释了为什么两周没有正反馈**：不是飞轮转得慢，是**飞轮少了一个齿**。通路一和三都断着，所以无论跑多少实验，结果都不会沉淀成能力。

## 2. 四齿逐一对照

### 2.1 第一齿：信号（评测）

博客说评测在自进化中有**三重职责**，而传统评测只有一重：

| 职责 | 含义 | 我们做了吗 |
|---|---|---|
| 质量门控 | 更新前验证"改了是否更好" | ⚠️ 设计了但没接通（#2c） |
| **方向指引** | 告诉系统"下一步往哪改" | ⚠️ 有诊断，但没流进修复链路 |
| **经验筛选** | 判断一次执行是"好经验"还是"该丢弃" | ❌ 基本没有（#5 #6） |

> 博客："传统评测打错分顶多是'这次上线了一个不够好的版本'；**自进化评测打错分是'Agent 学到了错误经验并持续污染后续所有任务'**。"

**七大难题里，我们踩了四个：**

| 难题 | 博客的警示 | 我们 |
|---|---|---|
| 一、弱评估器 | "错误的正反馈比没有反馈更可怕" | **#9** ContinualSkillBench 判分器实际在测 LaTeX 还原度 |
| 二、评什么维度 | "只评结果不评过程，盲区里的问题永远不会被发现" | 我们只看 `resolved`/`passed`，不看轨迹 |
| 三、评什么粒度 | "粗粒度只能'瞎改'" | 我们的 `failure_class` 归因算出来了却没回传 |
| **六、预算公平性** | "很多'自动进化'的提升可能仅仅来自多花了计算预算……**真正的进化应该是：在相同的 Token 预算下，Agent 也比之前做得更好**" | 我们记了 token 成本，**但没做预算对等的判定** |
| 七、评测成本 | "评测太贵导致一周只能跑一轮——飞轮就转得很慢" | 我们 69 题 × 2 臂跑了 5+ 小时 |

**评测集三分法**（train / val / test，严格职责分离）：我们做了 held-out，方向对。但博客强调 **val 集"绝不暴露给生成修复方案的 LLM"**——我们要检查 `refine.py` 有没有把测试任务的痕迹漏进去（我们的校验里有禁止 `/tmp/|fixture|EvoAgentBench|LiveCodeBench` 的规则，说明当时意识到了）。

**评估器本身也需要被评测**——博客给的具体做法：

> "维护一小批'**元评测集**'——几十条明确标注为'绝对正确'和'绝对错误'的样本。定期拿出来检查评估器是否还能正确识别。**如果评估器连这些极端 case 都判错了——它的所有打分都不可信，系统应该告警。**"

**这和文献里的行业规范是同一条**：SWE-bench 的 `--gold` 校验、Terminal-Bench 的 "oracle 通过 AND no-op 失败"、Microsoft Vally 的 `--no-golden-input` 负对照。**中文博客和英文论文给出的是同一个答案。**

### 2.2 ⭐ Skill 评测的四层验证——我们一层都没过

**这是全篇对我们最有用的部分。** 博客说"证明 Skill 真的有用比想象中难"，并提出四层验证：

| 层 | 博客的问题 | 我们的状态 |
|---|---|---|
| **一、对照实验** | "模型本来就会做吗？**如果无 Skill 时 Agent 也能做对——那 Skill 的'贡献'是零。** 很多团队跳过了这一步，导致积累了大量'看起来有用但实际无用'的 Skill——它们只是在浪费上下文窗口" | ❌ 我们**没有**无 Skill 对照下的**饱和基线认知**。自有 code 域 87%、LCB 套件 75%、SWE-bench train 100% |
| **二、难度校准** | "如果评测 case 本身非常简单……**对照实验看不出差异。** 需要设计有一定难度梯度的 case——让模型在'无 Skill 时能做对一部分但做错一部分'的水平上" | ❌ **#8** 四个池子里三个 75–100% 饱和。只有 LCB hard tier（20%）有余量 |
| **三、轨迹追踪** | "一个常见的假象：Skill 存在于上下文中，Agent 最终给出了正确答案，但实际上 Agent **根本没有 follow Skill 里的步骤**" | ❌ 我们 **skill 臂投递率只有 2/20 = 10%**，被 `CONSTRAINT_NOT_OBSERVED` 挡住——**连"存在"都没做到** |
| **四、路径验证** | "最隐蔽的问题：答案对了，轨迹里也出现了相关调用，但 Agent **绕过了 Skill 定义的关键校验步骤**碰巧得到正确结果。**路径不对意味着下次会翻车——即使这次结果对了**" | ❌ 完全没有 |

博客那句总结，就是我们的诊断书：

> **"很多 Skill 看似有效，实际上只是和模型能力碰巧重叠了——Skill 的存在只是'恰好和 Agent 本来就会做的事一样'。"**

**在 87% 通过率的池子上，我们测不出 Skill 的效果，不是 Skill 没用，是任务太简单。** 这和文献的饱和结论（SWE-bench Verified 前十名共享 285 成功 / 51 失败 ⇒ 只有 164 个有区分度的实例）是同一件事。

### 2.3 第二齿：积累（记忆）

博客的核心论断："**记忆做不好，比没有记忆更差**"，并说"把记忆系统当作一个**治理系统**而非存储系统来设计，是我认为最重要的认知转变"。

**写入环——"策展而非全存"：**

| 博客的做法 | 我们 |
|---|---|
| "**只有收到明确的正信号时才写入长期记忆**——用户确认/评测通过/任务成功" | ⚠️ 我们的 `_experience_runs` 只接受 `TASK_PASS`/`TASK_FAIL` |
| "**失败也有价值，但存法不同**：失败任务同样提取经验，但**标记为'反例/陷阱'**——'这条路走不通，因为 XX 原因'。**一个明确的反例比一个模糊的正例更有价值**" | ❌ **#5** 我们同一个 prompt、同一个 schema（见 `notes/wrong-practices.md` #5） |
| 三层晋升机制 | ❌ 我们没有晋升——一次写入就是终态 |
| **非对称淘汰设计**："好经验强化速度（+0.05）远慢于坏经验淘汰速度（−0.12）——**淘汰是强化的 2.4 倍**。逻辑：**一条错误记忆的伤害 > 一条正确记忆的收益**" | ❌ 我们**没有任何淘汰机制**。`frozen/refinement-r2/` 里的 24 条记忆和 1 个技能是永久冻结的 |

**写入环的难点 ②（正负反馈不对称）**：
> "任务成功时，你知道'做对了'但**不知道'因为什么做对'**——是 Prompt 好？还是碰巧数据质量高？归因难导致写入的经验可能归因错误。"

→ 我们的 22 PASS / 2 FAIL 全部归因不清，这正是**#6**。

**写入环的难点 ④（隐性知识难捕获）**：
> "最有价值的经验往往是'**什么不能做**'——'这个 API 的 timeout 不要用默认值'。Agent 很难自主识别这类'**负空间**'知识。"

→ 我们丢掉了 `failure_class` 和 `failure_reason`（**#4**）。**负空间知识我们一个字都没存。**

**存储环——生命周期管理**：版本控制 / 演化能力 / 主动遗忘 / 冲突解决。
我们有一半：`artifact_hash` 给了内容寻址，但没有版本演进、没有 TTL、没有冲突解决。

**存储环的难点 ⑤（记忆污染）**：
> "一条错误记忆被写入后，在被发现之前可能已经**影响数百次后续任务**。**错误蔓延速度远快于修复速度**——这是记忆系统最危险的失败模式。"

→ 文献侧同一件事：Library Drift 的 A4（`−0.019`，**低于"没有技能库"的地板**）；VaG 的"事后删源技能只挽回 17% 的退化"。

**读取环——渐进披露 + 严格预算**：

| 博客的预算 | 我们 |
|---|---|
| Skill ≤ 2000 token，Facts ≤ 800，Profile ≤ 500 | ❌ 无 |
| 单条 ≤ 200 token | ❌ 无——`refine.py` 允许 40–400 **字符** |
| **最多注入 6 条（少而精）** | ⚠️ `top_k ≤ 2`，比博客更保守 |
| 三路并行检索（语义向量 + 全文关键词 + 精确匹配）融合排序 | ❌ **#1** 我们用单路 `lexical-idf-v1` |

**一个大坑（难点 ⑩）**：
> "记忆注入占用有限的上下文窗口。注入太多 → 挤压工作空间 + 分散注意力。**没有自适应机制是通病**"

→ 我们**没有 Pain-aware 动态调整**——简单任务和复杂任务给一样多。这对应文献里 AutoGuide 的"按上下文检索"（47.1% vs ExpeL 每步全给 21.8%）。

### 2.4 第三齿：落地

博客的核心论断：**"自动化 ≠ 全自动"**，并给出**八个环节**。逐个对照：

| 环节 | 博客要点 | 我们 |
|---|---|---|
| ① 诊断归因 | "归因的粒度决定修复的精度" | ⚠️ 有 |
| ② 信号汇聚 | 三路：本轮诊断 + **历史 Playbook** + **外部知识**。"只看单一信号容易陷入局部最优——重复尝试同样的思路，导致**平台期停滞**" | ❌ 我们只有"本轮诊断"一路。**没有 Playbook，没有外部知识引入** |
| ③ 生成候选 | "**用 Diff 模式（只输出需要修改的部分），而非全文重写**——全文重写风险极大，容易覆盖无关的正确逻辑" | ❌ `refine.py` 是**全文生成** `SKILL.md` |
| ④ 独立评测 | 每个候选在**隔离环境**验证，不能互相干扰 | ⚠️ 我们有隔离，但选错了方式（**#3**） |
| ⑤ 安全门控 | **五层**：语法检查 → 回归检测 → **统计显著性** → Playbook 一致性 → 人工确认。"前四层全自动过滤 95% 低质变体" | ⚠️ **只有一层半**：`adoptionProof` 的 `newly_fixed≥1 ∧ newly_broken=0`。缺语法、缺显著性、缺一致性；人工确认在 UI 里但没接通（**#2c**） |
| ⑥ 灰度发布 | 10% 流量 × 7 天 + **自动回滚** | ❌ 无 |
| ⑦ 监控回流 | "**上线不是终点，而是下一轮进化的起点**" | ❌ 无（通路四断了） |
| ⑧ 经验沉淀 | 写入 **Playbook**。"**没有沉淀的系统，每一轮实验都是从零开始——同样的弯路反复走**" | ❌ **我们反复换仪器就是这条的后果（#7）** |

**五层门控里，我们最缺的是第三层"统计显著性"**——而没有它，`newly_fixed=2, newly_broken=0` 这种数字会被当成通过。文献侧完全一致：σ≈1.5pp 的噪声底上，2–3pp 的差异"可能只是评测噪声"。

**版本化一切**（建设要点四）：博客列出四项，Skill/Prompt/记忆的每次变更必须有 **版本号 / 变更日志 / 来源标记 / 关联评测结果**。

我们有版本号（`artifact_hash`、`base_version`）和来源标记，**但"关联评测结果"这一项正是通路三断掉的地方**。

**SkillOS 那条**：
> "业界调研指出：几乎所有系统默认用大模型来总结，但 SkillOS 研究证明**训练过的小模型策展人效果优于冻结的大模型策展人**。总结质量决定 Skill 质量，这个环节不能假设'用好模型就行'。"

→ 值得回头查 `refine.py` 实际用的是哪个模型做提炼。文献侧同一条：ExpeL 里 gpt-4 提炼 39.0 vs gpt-3.5 32.0。

**Dreaming（3.4）**：异步进程定期审阅一批历史轨迹，找**跨会话的系统性模式**。
→ 我们完全没有。而这正好补上前面的空缺：**单次评测看不到"反复出现的失败模式"**。

### 2.5 第四齿：控制

博客核心论断："**人的角色是教练和裁判，不是操作者**"，并提出分级自主 + 五个必须有人的节点。

**这个齿上我们反而做得不错**——线 A 的 `adoption.ts` 有 `FrozenAssetWriter`、review、人工确认的完整设计；线 B 就是人在回路。

但博客有一条**直接打中我们这个项目**的观察：

> **④ 新领域冷启动时的初始经验种子。**
> "没有历史数据的新场景，飞轮无法自动转起来——需要人提供第一批评测 case（告诉系统'什么叫好'）、初始 Skill（给出'大致怎么做'的方向）、安全边界。
> **试图跳过冷启动直接让 Agent 自己摸索，大概率的结果是在错误方向上快速迭代——越转越偏。**"

→ **我们的 24 条经验（22 PASS / 2 FAIL）就是"错误的初始种子"。** 用 87% 通过率池子产出的经验去做冷启动，飞轮从第一天就在错误方向上。

博客还给了**审核疲劳**的解法和一条判据：

> "到人手上的东西质量太差、数量太多……**如果每天收到 50 个审核请求，其中 48 个是明显可以自动过滤的低质变体**——人的注意力被垃圾请求耗尽。"

→ 我们的 `skill` 臂投递率 10%，意味着**人看到的候选里 90% 是垃圾**。这正好是审核疲劳的成因。

## 3. ⭐ 那条"血泪教训"就是我们

博客在"建设要点三：评测的终点不是打分，是诊断归因"里，写了一条：

> **一条血泪教训**：如果某个场景**连续 3 轮失败率 80%+ 不下降**——**先停下来查工具实现层**（API 参数错误、服务端返回异常、数据根本没回来），而非继续在配置层打转。**配置层的进化解决不了工具层的 Bug**——实践中出现过 **20+ 轮无效迭代、最终发现根因在工具层而非配置层**的案例。

**这就是我们。** 逐字对照：

| 博客 | 我们 |
|---|---|
| 连续 3 轮失败率不下降 | 两周、多轮实验，没有正面结果 |
| 继续在配置层打转 | 反复换 benchmark、反复调提炼提示词、反复改观察策略 |
| 根因在**工具实现层** | **根因在 `auxiliary` 隔离导致注入被整条跳过**——被测臂从来没拿到过注入（**#1 根因**） |
| 20+ 轮无效迭代 | 我们跑了多少轮？ |

**而且我们踩的正是"最容易被误诊"的那一类**：工具层没报错。`auxiliary` 是**按设计**跳过注入的，日志里写着 `→ auxiliary (skip session-init/mem/injection/L0/skill)`——**它工作得很正常，只是不是我们以为的那种工作**。

> 一条可操作的判据（值得写进流程）：
> **当连续 3 轮实验没有改进时，停止调整配置，去验证链路本身。**
> 具体到我们：如果第一周有人问过"被测臂拿到的 prompt 里到底有没有注入内容"，这个问题当天就能发现。

博客的落地路线：

| Phase | 周期 | 目标 | 人工占比 |
|---|---|---|---|
| **Phase 1：最小闭环** | **1–2 周** | 验证"评测能发现问题 + 记忆能记住教训"。**手动跑一遍完整闭环** | **80%** |
| Phase 2：半自动化 | 2–4 周 | Skill 自动生成 + CI 评测门禁 + 版本管理 + 评测集三分法 | 40% |
| Phase 3：飞轮运转 | 1–2 月 | 灰度 + 回流 + 异步 Dreaming + 渐进放权 | 15% |
| Phase 4：元进化 | 持续 | Auto-Research + 进化策略自优化 | 5% |

Phase 1 的说明里有这两句：

> "这一步的核心目的**不是自动化，而是验证闭环本身是否成立**——**如果手动都跑不通，自动化只会更快地暴露问题**。"
>
> "很多团队的错误是——**Phase 1 还没验证就开始搭 Phase 3 的基础设施，最后发现闭环本身就没跑通**。"

**我们干了什么**：直接去搭 Phase 3 的东西——4 臂因子设计、配对 McNemar、功率预注册、灰度式的多波次运行。**而 Phase 1 的"手动跑通一圈"从来没跑通过**，因为通路三（落地→生效）是断的。

**我们造了很多"高端"零件，但飞轮少了一个齿。**

## 5. 另一个观察：什么场景最容易跑通

博客观察了已跑通全闭环的案例（工单自动修复：解决率 <30% → 近 90%；内容推荐：真实 CTR；长期记忆：LongMemEval 显著提升），指出两个共同特征：

| 特征 | 含义 | 我们 |
|---|---|---|
| **一、评测信号来自真实业务指标，而非人工构造** | "真实指标天然不存在评测集漂移问题——业务在变，指标跟着变" | ❌ 我们用人造 benchmark，且**判分器本身就是坏的** |
| **二、闭环链路短、反馈延迟低** | "**实践经验表明 5 轮迭代内就能看到显著提升**——如果你设计的系统需要跑 20 轮才能看到效果，大概率团队早就失去耐心放弃了" | ❌ 我们一轮 69 题 × 2 臂跑 5+ 小时，且**一轮不产出任何能力**（通路三断） |

**这两条解释了"为什么两周没有正反馈"的第三层原因**：即使机制有效，我们的场景也**不符合飞轮最容易转动的形态**。

> 对我们的启示：**应该优先选一个"有天然业务指标 + 链路短"的场景做 Phase 1**，而不是继续在人造 benchmark 上加功率。

## 6. 文献侧的四条工程经验，直接对应我们的缺口

> 来源：`reports/agent-memory-production-survey.md`（生产架构调研）。这四条比任何一篇论文都更接近"该改哪一行代码"。

### 6.1 ⭐ 预算不是判断（这条是我们犯的错的原名）

> "每个系统都有体积上限；**它们对正确性都没有帮助**。**不要让体积护栏在内部被汇报成质量门。**"

**我们正是这么做的**：`refine.py` 的"≥2 条独立支持 / 40–400 字符逐字引用 / ≥2 个共享概念 token"是**体积与模式护栏**，我们把它当成"质量把关"汇报了两周。

文献侧同一条（VaG 的门控定价表）：schema 校验只值 **−2pp**，而行为 A/B 重放值 **−10pp**。

**改写我们的话术**：我们做的不是 quality gate，是 **fitness gate**（benchmark 回归）。这个说法才是诚实的，而且它是这个领域里**更稀有、更难做、更值钱**的那一类。

### 6.2 把 PRODUCER 和 SELECTOR 分成两个不同权限的组件

> Hermes 是最干净的案例：**一个急切的、无门的生产者**（`background_review.py`，提示词原文 "Be ACTIVE — most sessions produce at least one skill update"）配 **一个保守的、有门的、默认关闭的选择器**（`curator.py`）。
> Codex / Claude Code / Letta 把两个角色融合在一起，**结果一个门都没有**。
> **"如果只从这份调研里建一样东西，就把它们建成两个组件。"**

**我们的状态**：`refine.py` 同时做**生成**和**校验**——是融合形态。而线 A 其实是分开的（`proposals` / `proposal-runner` / `evaluate-gate` / `adoption` 各自独立）。

→ **所以正确的动作不是"改 refine.py"，是"把 refine.py 生成的东西交给线 A 的门"**。这和第八节接线图是同一件事，只是从架构角度又确认了一遍。

### 6.3 绝不要从系统自己的输出里学习

> OpenClaw 在摄入前**剥离被召回的上下文**："这样被召回的片段不会作为新记忆被再学一遍"。
> Hermes 传 `skip_memory=True`，防止 harness prompt 泄漏进 Honcho/Mem0/Supermemory。
> **两者都是观察到的真实失效模式。**

**对我们的意义（待查）**：我们 `refine.py` 的源轨迹（`phase4-memory-v1/frozen/refinement-r2/`，24 条）**如果当时带过注入内容，就是一个自污染回路**——早期记忆被召回、写进轨迹、又被提炼成"新"记忆。

**这是一个必须查的具体问题**：源轨迹的 `session.jsonl` 里有没有 `Retrieved experiences` 那段注入文本。

### 6.4 门要 fail closed，而且要在代码里证明

> "**Prompt 不执行策略；拒绝才执行策略。**"
> Hermes 的每个护栏都带着促使它诞生的 issue 号（#29912 是整个技能簇被归档而 `consolidated_this_run == 0`；#67140）。

**我们的状态**：线 A 的 `adoption.ts` 有这个精神（`withTargetLock` / `authorizeAndPrepare` / `verifyApplied`，注释写着 "a status label alone is not proof"）。`refine.py` 没有。

→ 值得抄的习惯：**给每个护栏写一行注释，说明它是被哪次事故逼出来的。** 我们已经有现成的素材——SWE-bench log parser 的 key/value 写反（#9）、四臂实验的 job 名覆盖（#5）、空响应被静默计入。

## 7. 结论：我们缺的是哪个齿

| 齿 | 状态 | 关键缺口 |
|---|---|---|
| 一、信号（评测） | ⚠️ 有但不合格 | 仪器没验（#9）；无轨迹/路径验证；无预算对等判定；无元评测集 |
| 二、积累（记忆） | ⚠️ 有但没治理 | 失败和成功同 schema（#5）；无淘汰；无晋升；无 token 预算；单路检索（#1） |
| 三、落地 | ❌ **基本没有** | 只有一层半门控；无 Diff 模式；无灰度；无回流；无 Playbook |
| 四、控制 | ✅ **相对最好** | 线 A 的 adoption 设计是对的，线 B 的人在回路是对的 |
| **衔接** | ❌ **断两条** | **通路三（落地→生效）完全断**；通路四（回流）断 |

**所以之前那个问题的答案变清晰了**：

> 不是 benchmark 选得不合适，也不是机制无效。
> **是我们的飞轮缺了"落地→生效"这个齿，所以无论跑多少实验，结论都停在抽屉里。**
> 而且我们在缺一个齿的情况下，还在给另一个齿加功率。

**修法的优先级**（按博客的框架，不是按我的偏好）：

1. **接通通路三**：让评测证据能进 `adoptionProof`。这是 `notes/wrong-practices.md` 第八节的"接线图"，补三个字段
2. **验仪器**：gold=1.0 / no-op=0.0 / 元评测集。**在接任何自动化之前**
3. **跑通 Phase 1**：手工跑一圈完整闭环（评测发现问题 → 记忆记住 → 生成候选 → 门控 → **生效** → 回流）
4. **然后再谈** 难度校准、Diff 模式、灰度、Dreaming、Power

**第 3 步只需要 1–2 周，人工占比 80%。** 我们两周其实跑的是 Phase 3 的东西。

## 8. 2026-09-22 更正：通路一不是"没治理"，是**被设计性切断**

上面的表格把第一齿写成"⚠️ 有但不合格"。跑完题族验尸实验后，代码给出的是更硬的结论：**评测通路接不进积累，是明写的设计，不是缺口。**

| 事实 | 位置 | 后果 |
|---|---|---|
| benchmark 证据**永不派发诊断** | `service.ts:353`（`research-only`）、`:434`（`never diagnosis inputs`） | **benchmark 无法闭环自进化**，`benchmark/*` 只记录研究证据 |
| 诊断只接受 `origin === "runtime"` 的 trace | `diagnosis.ts:34`（`LIVE_TRACE_REQUIRED`） | 只能靠**真实生产流量**产出候选 |
| 技能候选**只由 `skill_defect` 生成**，且需 ≥2 条被引用的 FAIL 轨迹 | `proposals.ts:12`、`diagnosis.ts:60` | **成功永不固化**；已做对的题学不到任何东西 |
| 其余路由（`no_change`/`infrastructure`/`capability_gap`/`unknown`）**不产出候选** | `dispatcher.ts:104` | `capability_gap` 这个最像"该学新能力"的路由，其实**没有任何下游** |
| 评测 attempt **不持久化 agent 转写** | attempt payload 只有 `paired_results`/`gate_result`/`cost_summary` | 评测路径连一条真实轨迹都产不出，必须另开旁路采集 |

**这三条合起来解释了"跑了一个月没有正结果"**：

> 我们一直在**用评测去找可迁移的技能**，而产品里评测根本不驱动积累；
> 唯一能驱动积累的是"**同一个 agent 连续两次做错同一类事**"——那是**缺陷修复**，不是能力增长。
> 自进化的适用面因此被限死在"模型持续做错的地方"，而这恰恰是最不像"进化"的那部分。

**修法优先级（修订）**：

1. **先决定飞轮要做哪件事**：修缺陷（现状，闭环存在但很窄）还是沉淀能力（需要新增"成功→可复用结构"的路由与证据形状）。**没有这一步，后面都是空转。**
2. **门禁加重复 + 显著性检验**。单次运行约 9% 概率误报 `newly_fixed`（见 `notes/wrong-practices.md` 10.15）；这比"接不通"更危险，因为它会**把噪声写进资产**。
3. **任务特定结构必须按任务路由送达**。产品有 bm25 routing，评测器却无脑注入单个候选——这是同一份技能在 A 题 +60pp、在结构不同的 B 题 0/10 的直接原因（10.16）。
4. 最后才是接通 `adoptionProof` / 灰度 / Diff 模式。
