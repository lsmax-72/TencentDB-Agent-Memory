# Phase 4 报告：复用 suite 上的 Memory 效果测量

日期：2026-09-15。协议：`tdai-evoagentbench-code-v13-memory-transfer`（`protocol_hash 6e405f5e…`）。候选：v8 composite r2（`a3691813…`）。

## 1. 结论

**本轮没有测到 Memory 的迁移效果，但原因不是"Memory 无效"，而是这套 suite 在修好的 harness 下几乎没有余地可测。**

| 项 | 结果 |
|---|---|
| 干净配对 | **23 / 24** |
| Memory 注入送达 | **23 / 23** |
| vanilla 通过 | 20 / 23（**87%**） |
| memory 通过 | 22 / 23 |
| 严重度完全相同的配对 | 21 / 23 |
| 主指标（严重度） | 均值差 **0.0**，95% CI **[0.0, 0.0]** |
| 共同主指标（二值） | 净收益 **+2/23 = +8.7pp** |
| 形式判决 | `INFRA_ERROR`（`abc370_d` 可复现超时，见 §4） |

## 2. 为什么不能把这个 null 说成"Memory 无效"

**（a）仪器没有分辨力。** 23 个干净配对里 vanilla 通过 20 个，**只剩 3 道可救的题**；主指标 CI 退化成 `[0,0]`，这不是"效应为零"，是"没有东西可修"。历史同 suite 的 vanilla 曾是 75%（25% 余地）——**那个余地是坏掉的 harness 造出来的假象**（截断、迭代耗尽、退化 run 被记成能力失败）。

**（b）二值指标上的 +2 道正好等于实测噪声底噪。** 零送达配对上测得的噪声是 **±2 题**（v4 那次"送达率 0% 却 +2 题"就是这个量级）。所以 +2/23 **不可解释为效果**。

**（c）两个指标矛盾，且矛盾有具体原因。** 严重度说 0.0、二值说 +2：因为**恰好是那两道被 Memory 修好的题**（`3603`/`abc342_e`/`abc380_f` 一类）**没有已冻结的套件规模**，按预注册规则被排除在严重度之外。这暴露严重度指标的一个真实限制：**当收益恰好落在规模未知的题上时，主指标会系统性漏报**。本轮无法用严重度验证那 2 道题，也就无法给出"有增益"的结论 —— 唯一能说的是"不可归因"。

## 3. 因此本轮的可信结论只有两条

1. **投递链路可靠**：23/23 送达，与 v12 正对照一致。
2. **这套 suite 不能用来测效果**：修好 harness 后 vanilla 已达 87%，可救题仅 3 道。任何在此 suite 上得到的正/负结果都缺乏分辨力。

关于 Memory 是否迁移：**本轮既未证明也未排除**，受限于仪器而非资产。

## 4. 新发现的基础设施缺陷：16k 输出预算与 proxy 的 5 分钟上游超时冲突

**症状**：`abc370_d` 两臂、以及 `abc388_e` 的部分 run 记录为 `INFRA_ERROR`，判分器结果 `0/0`。

**真因**（proxy 容器日志实证）：

```text
[01a0a5ca] → FORWARD upstream=http://10.195.214.152:8100/v1/chat/completions
15:58:16 → 16:03:20  ERROR stage=FORWARD error="fetch failed" TypeError
```

每次 forward **恰好 5 分 04 秒**后失败 —— proxy 到上游有 **5 分钟超时**，而请求是**非流式**（`stream=false`）。v9 起把 `max_output_tokens_per_call` 从 8192 提到 **16384**，使部分单次生成超过 5 分钟 → 超时 → 502。

**这是 v9 runner policy 引入的新失效模式**，本批 4/48 个 run 命中（8%）。建议后续协议二选一：降低单次输出预算，或让 agent 走流式请求（流式可避免长生成触发整体超时）。

**已修的两个可诊断性问题**（不改变测量语义）：

1. **502 曾被"用量缺失"盖住**：`adapt_trial` 现在记录 `proxy_error_statuses`，并在设备层把上游 5xx 与"没有用量字段"区分开。修复过程中还发现该字段在"无 usage 提前返回"路径上会丢失 —— 而那正是 502 的路径，已修并加测试。
2. **一次已自愈的瞬时失败曾作废有效结果**：`abc388_e-vanilla` 实际拿到 **43/43 满分**，却因 11 次调用里有 1 次 502 导致用量求和为 null 而被判 `INFRA_ERROR`。现在：若判分器已给出有效结果（`verifier.total > 0`），只把用量记为 `USAGE_EVIDENCE_INCOMPLETE`，**保留这次测量**；只有确实没有结果的（`0/0`）才仍是 `INFRA_ERROR`。修复后 `abc388_e` 两次运行被正确救回。

## 5. 历史读数需要系统性更正

同一套题在 **v13**（修好的 runner policy）下 vanilla 87%，而历史记录是 75%（v2）甚至更低。差额来自：

- 输出截断（13% 的 run 有调用触顶）
- 工具迭代耗尽（如 `abc388_e` 旧的 12 次上限）
- 退化 run（单次调用、零工具、输出触顶）：占 v2 失败的 73.7%、v4 的 76.9%

**任何基于 v9 之前数据估算的"余地"都不可信。** 这一结论已在功效预注册文档与 harness 退化报告中同步。
