# 官方博客与实测结论的对账

> 对象：《任何错误只犯一次：TencentDB Agent Memory 的团队记忆实践》（腾讯技术工程，2026-08-18）
> 本地剪藏：`/Users/lsmax/Develop/Clippings/任何错误只犯一次：TencentDB Agent Memory 的团队记忆实践.md`
> 对账对象：`notes/wrong-practices.md` 第十/十一节、`docs/flywheel-gap-analysis.md`、`docs/swebench-instrument-audit.md`
> 目的：说清哪些结论互相印证、哪些并不冲突（因为测的是不同东西）、哪些是**博客主张与代码现状的冲突**。

---

## 0. 一句话

**博客测的是"检索并装配已有资产"，我测的是"从失败自动生成技能并采纳"。这是两个不同的环；我的阴性结果否不掉博客的 60%→80%，博客的阳性结果也覆盖不到我测的那条链路。**

但两者有一处**硬冲突**，而且冲突在代码里：博客明确设计的是**渐进式暴露**（不把资产整份塞进 Prompt），而**评测器把整份资产原样包进 `<evaluation_skill>`**。这意味着我的实验测的是一种**与产品设计相反的投递方式**。

---

## 1. 两条被混淆的链路

| | 博客 §5 的链路 | 我一个月测的链路 |
|---|---|---|
| 机制 | **检索已有资产**：找到时间有效、项目相关的前序 Case，装配它的资产 | **自动生成资产**：`task/complete` → 诊断 → 候选 → 门控 → 采纳 |
| 输入 | 历史任务库（2,600 Session / 5,081 Task / 22,361 Relation） | 同一 agent 的失败轨迹（≥2 条被引用的 FAIL） |
| 需要诊断吗 | **不需要** | 必需（`LIVE_TRACE_REQUIRED`） |
| 资产来源 | 已有、经审核、带 Scope/Version/ACL | 模型当场生成，尚未验证 |
| 度量 | SWE-bench 相关 Case：完成率 60%→80% | 合成题族：合并 9:4，精确 McNemar p=0.27 |

**结论：这两组数字不能互相印证，也不能互相否证。** 博客的 60→80 里没有一步依赖 `diagnosis/candidate/adoption`。

## 2. 互相印证的地方（同一个现象，两组独立证据）

| 博客的观察 | 我的实测 | 关系 |
|---|---|---|
| §3.3：**逻辑返工 1,350 条 ≫ 缺少上下文 269 条** → "团队记忆不能只做'找资料'，还要保存决策理由、失败路径、适用条件和验证方式" | 四臂对照：注入**完整算法** ≈ **部分结构** ≈ **完全无关内容**（C vs B **p=1.000**）；起作用的是**任务结构那一节**，不是知识内容 | **同一方向**。博客从卡点分布推出来，我从对照实验测出来 |
| §3.2："**关联不等于复用，复用也不等于可以直接执行**"；`same_problem` 精度只有 **69.00%**，低于预设 70% 门槛，选择**如实保留为已知风险**而非调口径 | 同一个候选在自己那道题 7/10、换到结构不同的题 **0/10**（p=0.0031） | **同一现象的两个尺度**：博客是"选了但用不了"，我是"用错了直接归零" |
| §4.2 原则："**禁止未来信息泄漏**"、"**资产优化需要负例**"、强/弱/Shadow 三级置信 | 我的第 10.6 节就是一次真实的未来信息泄漏（agent 上网把题面抄回来）；门禁无重复无显著性检验，单次运行约 **9% 概率误报 `newly_fixed`** | 博客把这两条列为原则；我测出违反它们的**具体代价** |
| §6.1 原则五："**错误召回不能只依赖下一次模型'自己判断'，人的负反馈必须改变后续路由**" | 门禁只有一个模型判定、无重复、无显著性检验，且 `newly_fixed>=1 ∧ newly_broken==0` 就足以放行 | **同一个问题的两个面**：判据太弱 = 依赖单次模型判断 |
| §5.3 自己承认：需要"固定评测子集、报告样本数与置信区间，**区分资产帮助、无影响和负迁移**" | 我一个月撞的就是这三件事；我的留出实验正好产出 `+18pp 均值 / p=0.27 / 4 次负迁移` | **博客预判了我的结论形态**。它不是过度宣称，而是明确留了缺口 |

**这一组说明：我的失败是"缺治理与判据"，不是"记忆没用"。** 博客其实把它写成了设计原则，只是没有用测量去闭合。

## 3. 博客主张 vs 代码现状：四处冲突

这四点是本次对账真正新增的东西。

### 3.1 ⭐ 渐进式暴露 vs 整份注入（最重要）

博客 §2.3.3：

> **分层装配的最后一步，不是把选中的资产全部复制进 Prompt。** Chat Memory 可以先提供场景摘要…**Skill 可以先暴露名称、触发条件和用途，确定适用后再加载完整步骤和资源文件**；Wiki 和 CodeGraph 只注入资源名称、Summary 和工具入口…**Prompt 承担的是"告诉 Agent 有什么、为什么可能有用"，工具调用承担的是"在需要时拿到细节"。**

代码现状（评测路径）：

```
minimal-runner.ts:354   return `<evaluation_skill>\n${content}\n</evaluation_skill>`;
```

`content` 就是 `artifact.content` 原文，**无截断、无摘要、无"先给入口"**。我的实验里两臂分别注入 **18,512 / 20,897 字符**的整份技能。

**后果（这条解释了我自己的旧结论）**：10.15 发现"效果跟着注入文字的**长度**走"（1748 → 2516–3243 字符）——在**整份注入**下，这更像**注意力/长度效应**，而不是机制本身的效果。产品真正要上线的是渐进式暴露，**而评测器测的是它的反面**。

> 所以评测结论对生产行为的**可外推性比我想的更差**：我测的不是"这个技能会不会有用"，而是"把这份文档全文塞进 prompt 会不会有用"。

### 3.2 按任务装配 vs 无脑注入单个候选

博客 §2.3.2 的装配顺序是五层：身份/ACL → 固定绑定 → 浮动召回 → **BM25 + 向量 + RRF 融合** → 上下文装配（Memory Pack）。

评测器只做一件事：把**一个候选**的技能全文塞进去，**没有路由、没有相关性竞争、没有长度预算**。这正是 10.16"结构对不上就归零"的直接原因——产品里本该由 RRF 拦掉的错误注入，在评测器里没有任何拦截。

### 3.3 验证后升级 vs 评测证据进不了诊断

博客 §2.5 第 4 步："**验证后升级**：未经验证的轨迹先作为低权重背景；能够被测试、提交或人工 Review 支持的内容，才逐步进入更稳定的场景记忆或共享 Skill。"

代码现状：

```
service.ts:353  // Benchmark evidence is research-only. It is not an adoption proof and never dispatches diagnosis.
service.ts:434  // Development/test runs are visible research evidence, never diagnosis inputs.
diagnosis.ts:34 if (trace.kind !== "trace" || trace.origin !== "runtime") throw ... "LIVE_TRACE_REQUIRED"
```

博客描述的"验证 → 升级"回路，**在 benchmark 这条路上是断开的**：验证结果进不了诊断，所以"验证"无法驱动"升级"，只有真实生产流量能。

### 3.4 SWE-bench 数字的仪器前提

博客 §5.1 报告的 60%→80% 建立在 SWE-bench 之上。我的审计（`docs/swebench-instrument-audit.md`）在同一套栈上发现：

- 官方日志解析器**键值颠倒**，导致 **9.2% 的题恒判 0**（已修复并验证）；
- **天花板题**：`psf__requests-2931` 连 gold patch 都拿不到 `resolved`（Docker 网络下 TARPIT 超时语义与参考环境不同）；
- 代理地址被原样塞进容器；agent 一旦 `git add/commit` patch 读成空。

这些**同向偏置两臂**，不改变差值的方向，但意味着：**在固定评测子集 + 置信区间 + 负迁移分类补齐之前，60%→80% 缺少一个可信的仪器前提**——而这恰好就是博客 §5.3 自己列出的待办。

---

## 4. 因此我要修正自己的结论

`notes/wrong-practices.md` 11.8 写的"自进化没有可复现的正面效果"，必须**限定范围**：

| 结论 | 适用链路 | 置信度 |
|---|---|---|
| 没有可复现的正面效果 | **自动生成技能并采纳**（`diagnosis → candidate → gate → adoption`） | 高（多轮对照 + 题族留出） |
| 结构对不上时明确有害 | 同上，且**评测器无路由**放大了它 | 高 |
| 只能修缺陷、不能固化能力 | 同上（`proposals.ts:12` 要求 `skill_defect`） | 代码事实 |
| **未测** | **检索并装配已有资产**（博客 60→80 的那条链路） | **无结论** |
| **新增** | **评测器的整份注入违反产品自己的渐进式暴露原则** | 代码事实 |

**所以正确的说法是**：不是"团队记忆没用"，而是"**我一直在用评测去驱动一个评测本就驱动不了的环，而且用的还是一种产品不会采用的投递方式**"。

---

## 5. 这份对账带来的两条可执行修正

1. **评测臂必须按产品的投递方式构造**。要么实现渐进式暴露（只给名称/触发条件/用途 + `/v3/tools/list`、`/v3/tools/call` 取细节），要么至少做到**按任务路由 + 长度匹配**。否则任何"技能有没有用"的评测都在测一个 off-design 的 prompt 长度效应。
2. **修判据之前不要再跑效果实验**。博客 §6.1 原则五和 §5.3 已经把要求写清楚了：重复、置信区间、负迁移分类、固定子集。在这四条补齐前，任何显著性结论都会被约 9% 的单次误报率污染。

**顺带**：博客 §2.7 那条"读档"案例（CodeGraph impact 工具）给了一个比我的合成题族好得多的评测素材形态——**同仓库、真实约束、可验证的跨文件检查清单**。若要继续做效果实验，应当用这种素材，而不是自造题族。
