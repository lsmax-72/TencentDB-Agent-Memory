## 1. 我们卡在哪：Phase 4 的三个障碍

回顾本项目 v9–v13 的实际结论：

| 障碍 | 证据 |
|---|---|
| ① **干预送达曾经为 0** | 历史技能送达 0/24、1/12；修复后 v12 达到 5/5、Phase 4 达到 23/23 |
| ② **仪器没有分辨力** | Phase 4：复用 suite 在修好的 harness 下 vanilla 通过 87%，可救题仅 3 道 → 主指标 CI 退化成 [0,0] |
| ③ **无法归因到"技能"本身** | 我们只有 `vanilla` vs `有资产` 两臂。一旦出现增益，**无法区分是"资产内容有用"还是"只是多保留了上下文/反馈"** |

障碍 ③ 是本项目**结构性缺失**，而 ContinualSkillBench 的第三臂正好补它。

## 2. 最重要的发现：ContinualSkillBench（已核实）

[ContinualSkillBench](https://arxiv.org/abs/2608.03874)（Guan et al., 2026-08），标题即问题：《Can LLM Agents Truly Evolve Their Capabilities?》。

### 2.1 设计（正是我们缺的仪器）

| 维度 | 设计 |
|---|---|
| 定位 | **首个动态评测框架**，专为 in-context 持续技能学习 |
| 域 | **5 个**：医疗 / 法律 / 数学 / 金融 / **办公自动化** |
| 题量 | 每域 **100 个相互关联的子任务**，按难度递增，**显式设计跨任务技能复用机会** |
| 模型 | GPT-4o、GPT-5.3-Codex、Claude 4.7 Opus |

### 2.2 三臂设计 —— 我们必须照搬的部分

| 臂 | 定义 | 对应我们的 | 
|---|---|---|
| **Independent** | 每题独立完成，**每题前重置技能库** | vanilla（无资产） |
| **Sequential** | 跨 100 题**维护并更新技能库** | memory / skill 臂 |
| **Pure ICL** | **保留先前上下文与反馈，但不允许创建或修改显式技能** | **我们没有这一臂** |

**Pure ICL 是本次最关键的收获。** 它把"资产内容"的贡献与"单纯多保留上下文/反馈"的贡献分开。没有它，任何正向结果都无法归因到技能/记忆本身 —— 这正是我们 Phase 4 无法给出结论的原因之一。

### 2.3 它的结论与我们的发现互相印证

| ContinualSkillBench 的结论 | 我们的对应发现 |
|---|---|
| Sequential 在 15 个 model–domain 组合中 14 个优于 Independent，总增益 **16.9%** | 投递修复后干预确实能改变结果（v12 `RESPONSIVE`） |
| **Pure ICL（0.605）≈ Sequential 带技能（0.602）** → 增益几乎全部来自**保留上下文**，而非技能抽象 | 我们从未分离这两者；我们 Phase 4 的二值 +2 正好等于噪声底噪 |
| 技能"**仍难以稳定固化为健壮且可迁移的技能**" | 我们 v11 的资产不 decisive；v12 唯一决定性的是"环境约定"而非算法知识 |
| **仓库膨胀**：弱模型积累更大更碎片化的技能库（GPT-4o ~384 个、复用率低；GPT-5.3-Codex ~205 个、复用频繁） | 我们 24 条 memory 只用到 11 条、top-2 集中度 0.5 —— 同一现象 |

### 2.4 相邻工作

[SkillLearnBench](https://arxiv.org/abs/2604.20087)（COLM'26，已核实）：20 个真实任务上评测持续学习/技能生成方法，结论"**没有方法在所有任务和 LLM 上都领先，换更强 LLM 也不一定有用**" —— 再次印证"资产质量是瓶颈，换模型不解决"。
SkillRevise（2606.01139）：trace-conditioned 技能修订，与我们的 trace patch 路线同源。

## 4. 方法论层面可直接引用（外部权威依据）

### 4.1 「论文四问」—— 我们的实验设计检查表

1. 改进是否**持久**（不是一次性涨分）
2. 改进是否**可迁移**（跨任务 / 跨 Harness / 跨模型）
3. 评测器是否被**污染**（hidden-set 密封、评测器冻结）
4. 有没有改到「**改进机制本身**」（元递归）

> **对号入座**：本项目 v9–v13 **栽在第 3 问**（harness 故障被当成能力失败、对照污染、preflight 预测错位）。第 1、2 问尚未测。这张表可作为后续所有实验的准入清单。

### 4.2 通用安全设计五原则 —— 我们已全部符合

| 原则 | 我们的实现 |
|---|---|
| 冻结评测器 | 协议 hash 冻结、判分不可改 |
| 有界变异 | patch budget、冻结 revision、只允许有界 add/delete/replace |
| 保留 / 回滚 | 严格改善才接受；失败 Attempt 保留不覆盖 |
| 谱系可审计 | immutable attempt + hash 贯通 + `superseded-attempts/` |
| 隐藏集验证 | held-out 分区、candidate-blind 校验 |

### 4.3 Headroom-Closed Index（HCI）

论文《The Last AI Built by Humans》(2609.11873, 未核实) 提出 **HCI 量化模型的自我改进天花板**。**这正对应我们 Phase 4 的"没有 headroom"困境** —— 若该指标可用，就能在**选 suite 之前**判断是否还有空间，避免再一次白跑 48 个 run。值得优先核实并引入。

### 4.4 成熟度路线图 L1–L5

| 级别 | 能力 | 我们 |
|---|---|---|
| L1 | 执行自治（完成预设改进操作） | **← 我们在这里** |
| L2 | 策略自治（自主选择改进策略） | 未达（协议与资产仍人工设计） |
| L3 | 经验获取自治（判断什么值得学） | 未达 |
| L4 | 环境适配自治 | 未达 |
| L5 | 元递归自治（改进机制本身可自优化） | 未达 |

**定位说明**：本项目目前是 L1，任何"已实现自进化"的表述都会超出实际。

### 4.5 五大改进维度

参数进化（SEAL）/ 上下文进化（Prime Agent）/ **记忆进化（ReasoningBank）** / **技能进化（SkillOpt、TRACE）** / Harness 代码进化（Darwin Gödel Machine、SkillSmith）。
**我们的 Memory 臂 = 记忆进化，Skill 臂 = 技能进化，runner policy 修复 = Harness 代码进化。**

## 6. 执行安全与隔离要求（必读）

**问题**：接入第三方 agent benchmark 会不会直接操控本机、造成损害？

**结论**：benchmark 本身只是代码；**真正会执行动作的是它驱动的 Agent**。因此风险取决于它如何执行，而**可以通过隔离控制在可接受范围**。

### 6.1 风险分级

| 情形 | 风险 | 判断依据（须审查后确认） |
|---|---|---|
| 纯 API 文本任务，本地只跑 Python | 低 | 不调用本地 harness、不写工作目录外 |
| 驱动**本地 coding harness**（Codex CLI / Claude Code 等） | **中** | 这类 harness 默认**写文件 + 执行 shell**；动作由远端模型决定、在本机执行 |
| 无沙箱、直接在宿主机工作目录跑 | 中偏高 | 可能越出工作目录、占满磁盘、污染仓库 |
| 仓库本身恶意（供应链） | 低但非零 | 学术仓库概率低，但必须假定不可信直到审查过 |

从公开描述看，ContinualSkillBench 评测的是前沿模型在 agent 场景下的表现，**大概率属于第二类**，因此**按"它会执行动作"准备**。

### 6.2 强制清单（接入任何第三方 benchmark 前）

1. **先只读审查，不运行**：确认是否调用本地 harness、是否用容器、挂载了什么路径、是否需要模型密钥、输出写到哪里。
2. **不在宿主机直接跑**：在容器/VM 内运行，且
   - 任务数据**只读**挂载
   - 独立 **scratch 工作区**，不挂载 `$HOME`、不挂载本项目仓库
   - **不开宿主网络**，仅放行模型 API 的出站
   - 限制磁盘与时长
3. **凭证最小化**：用受限/临时模型 key；凭证**不挂进工具容器**（沿用你业务线的做法：golden / 评分器 / 凭证不挂载到工具）。
4. **先确认写入位置**：跑第一条之前，明确输出目录；跑完核对没有越界写入。
5. **保留证据**：沿用既有纪律 —— 失败 Attempt 保留、不覆盖。

### 6.3 我们已有的安全范式（可直接复用）

业务线已实现的组合（见 `docs/business-memory-transfer-report.md`）：

> 工具仅 `spreadsheet_python`，20s/次、**无网络 Docker，输入只读**；golden/评分器/凭证**不挂载到工具**

EvoAgentBench 侧同样有 `tools: restrictToWorkspace: true` + 每 run 独立 `HOME`。**接新 benchmark 时照抄这套，而不是降低标准。**

## 7. 对下一步方案的修正

**原方案（v13/Phase 4）的问题**：在 EvoAgentBench 的枯竭题池里继续找难题 —— 官方 train 仅剩 14 题，且这套题在修好的 harness 下已无 headroom。

**修正后的建议**：

1. **换仪器**：采用 ContinualSkillBench 的题集结构（5 域 × 100 题、难度递增、显式跨任务复用机会）。
2. **补第三臂**：`Independent` / `Sequential` / **`Pure ICL`**。这一臂是"可归因"的前提。
3. **抗污染构造**：参考 GDPevo 的"规则杂交构造训练/测试"。
4. **先解决域不匹配**：ContinualSkillBench 的域是医疗/法律/数学/金融/**办公自动化**，**不是编程**。我们现有 harness 只跑 `code_implementation`，需要扩展；但**办公自动化/表格域恰好是 TencentDB Agent Memory 的真实用武之地**，也与既有 `scripts/business-memory/` 一致。
5. **接入前先做两件只读工作**：
   - 只读审查 ContinualSkillBench 代码（GitHub：`gtynnn060110-hash/continual-skill-bench-final`，**未经核实**）
   - 核实 HCI 论文（2609.11873）是否有可操作的"先验 headroom 判断"方法
